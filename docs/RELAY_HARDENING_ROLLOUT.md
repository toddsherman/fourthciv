Protected-preview cache and delayed-read/concurrent-write checks passed before this production build.

**Reviewed gate exception:** the existing production relay was already returning 503. A separate private build, never promoted, ran read-only `SELECT 1` with the existing protected production credential. It failed with sanitized evidence `configured: true`, `NeonDbError`, `quotaMentioned: true`, and no authentication flag. No raw database message, credential, or endpoint was emitted. This established a quota-related failure without establishing exact compute usage or a reset date. A fresh production history snapshot and successful database-backed candidate checks were unavailable, so they were explicitly deferred rather than recorded as passing. The exact tested code was installed before quota recovery to prevent the previous continuous SQL polling from resuming by default.

The complete signed-event backup captured at `2026-09-24T05:11:39.801Z` retains all 39 events and the original epoch. Deployment `dpl_DHpwN8LJXrFnfYYzV8WfkpgDYeEW` remains available for rollback. No production event was posted or replayed; no schema, event data, environment variable, or billing plan changed. One reversible project setting excluded this relay from paid Observability Plus; team settings and other projects were unchanged. The diagnostic build was not the promoted artifact.

After promotion, database-backed requests still returned the same 503. An invalid query returned an uncached 400 from the new handler, confirming the deployed code but not successful synchronization. **Production recovery verification remains outstanding:** re-read and verify the retained event IDs, signatures, digest, and epoch; establish successful cached reads and installed-Mac CDN hits; then observe actual suspension and usage. No production performance or cost savings have been measured. See [validation](VALIDATION.md) and [the free-pilot plan](FREE_PILOT_PLAN.md).

This exception is specific to the confirmed outage and unchanged database configuration. It does not replace the normal promotion gates below. Rolling back would restore continuous database polling after recovery; pair any rollback with pausing unnecessary test Macs while preserving all history.

## Isolated preview

1. Confirm preview/development point to the separate development database, never production. Keep preview deployment protection enabled. Use only synthetic events there.
2. Set a dedicated sensitive `FOURTHCIV_REQUEST_KEY` (64 random hex characters) for preview. Do not display or commit it. Apply `relay/schema.sql` through `npm run migrate`. The migration adds request tables/functions and preserves event IDs, counters, and epoch; existing publication limits remain unchanged.
3. Deploy the exact candidate to a preview of the relay project. Verify discovery/health and signed event round-trip with the existing CLI through the authorized preview access path. A protected preview may require an operator-only harness that supplies the platform bypass header; never disable native TLS verification or publish the bypass token.
4. Verify Vercel supplies trusted source metadata: make one normal read and one read with forged `x-forwarded-for`, `x-real-ip`, and `x-vercel-forwarded-for` values. From operator-side database assertions, confirm the two requests increment the same pseudonymous client counter. Do not return raw addresses, digests, secrets, or diagnostic endpoints publicly. The shared handler's local tests cannot prove platform header replacement.
5. Exercise HTTP 429/minute recovery on the isolated preview, using a test clock at the database layer or deliberately seeded test counters. Verify another independent source remains admitted. Do not flood the public relay. Real simultaneous transactions from separate database connections should preserve both source and global limits.
6. Confirm malformed requests, missing configuration, signed event deduplication, and stored history behave as documented. Clear synthetic test data only within the explicitly disposable preview environment.

## Production promotion

1. Before changing production, snapshot its epoch, event count, event IDs and signed envelopes through an access-controlled operator path. Retain the previous deployment and a database backup. Keep credentials and host identifiers out of reports.
2. Provision the independent production request key and apply additive schema changes only when required by the candidate. The September 12 migration preserved the previous request counters/functions and initialized new admission counters once; do not repeatedly recreate or clear them. The September 24 cache rollout reused the existing schema and environment without migration.
3. Build the exact verified relay source as a production-target deployment using production environment values, initially with `--prod --skip-domain`. Never promote the preview artifact backed by the development database into production. If sensitive database values cannot be exported, an independently reviewed, deployment-specific build migration may use the existing production environment directly; keep it out of the runtime and emit only safe validation summaries. Keep the previous production alias active until the new build, migration, and checks pass, then promote that production-target deployment. Confirm health and discovery advertise the new limits, existing history/epoch is unchanged, and installed alpha.11 hosts still synchronize. Prefer existing signed events for read-only production validation; new public test posts require an intentional operator decision because they persist.
4. Record the deployment ID, source commit, time, checks, and any faults in `VALIDATION.md`. Monitor existing host diagnostics and operator-side counters during the first day; this document does not create a scheduled monitor.
5. If validation fails, restore the previous deployment while preserving events and epoch. Leave additive tables/key in place until a reviewed cleanup; do not restore an old event snapshot over newer public messages. Record which earlier weaknesses return: for the September 24 cache rollout, rollback restores continuous SQL polling and needs the corresponding pause/usage precautions.

Publish a new Mac build only after its own signing, notarization, download, update, and installed-app checks. The friend checklist is in [PILOT_HOST_GUIDE.md](PILOT_HOST_GUIDE.md).
